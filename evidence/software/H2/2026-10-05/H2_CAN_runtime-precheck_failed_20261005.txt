Interpretation at capture time
------------------------------
- Both MCUs, RTOS schedulers, and UART logs were running.
- Each node queued exactly three CAN messages, filling the three hardware mailboxes.
- No mailbox became free afterward; tx_fail increased continuously.
- Neither node observed a FIFO0 interrupt or a valid received frame.
- hal_err=0x00200000 is HAL_CAN_ERROR_PARAM in the STM32F1 HAL and is a downstream result of calling HAL_CAN_AddTxMessage while no transmit mailbox is free; it is not by itself the physical root cause.
- ESR values showed repeated CAN error/bus-off recovery activity.

Retrospective physical review
-----------------------------
ST UM1724 Figure 13 and Table 27 place PA12 on CN10 pin 12 and PA11 on CN10 pin 14, both in the board-edge/even column. On-site inspection confirmed that both nodes already use this outer/even column; the earlier image-only conclusion that both used the inner/odd column was incorrect and is withdrawn. Node B has brown TX on PA12 and yellow RX on PA11. Node A has those two signals swapped: yellow on PA12 and brown on PA11. The Node A TX/RX swap is the leading cause to correct before another powered test.

Disposition
-----------
FAIL / HOLD. Stop the formal 60-second test. Disconnect both USB cables, leave Node B unchanged, and swap only Node A's brown/yellow jumpers within the same outer column so brown TX reaches CN10-12/PA12 and yellow RX reaches CN10-14/PA11. Visually verify Node A while unpowered, then repeat the short precheck.

Follow-up after Node A TX/RX correction
---------------------------------------
- The user powered both boards off and swapped only Node A's brown/yellow signal jumpers in the same board-edge/even column.
- Node A was then powered again and both VCPs were sampled simultaneously for approximately 15 seconds without reflashing.
- Node B wiring and all other low-voltage connections were left unchanged.

Follow-up interpretation and disposition
----------------------------------------
- The retry still failed in the same mode: both nodes retained exactly three queued frames, no mailbox became free, and neither node received a frame.
- Correcting Node A's reversed jumpers did not restore communication, so that wiring defect was not the only root cause.
- The official CAN Pal wiring guide connects MCU CAN RX to CAN Pal RX and MCU CAN TX to CAN Pal TX; no further blind TX/RX reversal is authorized.
- Formal 60-second acceptance remains on HOLD. The next diagnostic is a single oscilloscope check of Node A PA12/CAN Pal TX to determine whether the MCU is producing the expected logic-level CAN bitstream before changing firmware or bus wiring again.
